# 空き情報 保存・配信・日時検索サービス（試作）

5施設の毎時取得に、専用Workerへの保存とAPIからの読み戻し照合を接続する試作です。
D1とWorkerの初期設定は利用者が実施済みです。5施設の取得・保存・読み戻し一致を確認しました。稽古ノートへの組み込みは未完了です。
日時検索を追加したworker.mjsは、Cloudflareへの差し替えデプロイが必要です。GitHubのコード更新だけではWorkerは更新されません。

## 用途

GitHubの取得処理から施設ごとのデータを受け取り、Cloudflare D1に最新の状態を保存し、アプリに返します。
既存の端末通知用Workerとは別のWorkerとして運用する想定です。
予約表の団体名・予約表原文・座組メンバー情報は送信対象にしません。

## ファイル

- worker.mjs：Cloudflare Worker用のHTTP処理とD1の作成用SQL（SCHEMA定数）。
- worker.test.mjs：Node標準テストと実際のインメモリSQLiteによる検証。
- payload_export.py：既存解析結果から送信項目だけを取り出すアダプター。自己テスト付き。通信処理は含みません。
- collect_and_send.py：取得処理を呼び出し、原文を除いた結果を専用Workerに送信。
- sender_test.py：固定送信先・転送拒否・トークンと容量制限の検証。

## テスト（外部サイトへのアクセスなし）

Node 24以降で `node --test availability-service/worker.test.mjs`。
Python 3で `python3 availability-service/payload_export.py` と `python3 availability-service/sender_test.py`。
Pythonアダプターは標準ライブラリのみ。Nodeテストも追加パッケージ不要です。
D1への初回書き込みは確認済みです。CPU時間と継続運用時の利用枠は未測定です。

## API

- GET /health：サービス名・スキーマ・試作段階を返します。DB疎通を示すものではありません。
- POST /ingest：AuthorizationヘッダーのBearerトークンが必要です。1施設1回ずつ送信。
- GET /availability?facility=hiranuma：指定施設の現在の検証状態を返します。
- GET /facilities：公式資料で確認した時間帯・部屋名・利用上の注意・出典を返します。
- GET /search?date=2026-10-24&start=13:00&end=17:00：5施設から指定時間に合う部屋を検索します。facility=hiranumaなどを付けると1施設に絞れます。

入力は schema_version=1、facility、checked_at（UTC秒単位）、result（ok/error）、cells のみ。
cellsはroom/date/period/statusのみ。失敗報告は空配列、成功報告は1～1500枠。
1送信256KiBまで。取得時刻が24時間より古い、または5分を超える未来なら拒否します。

## 誤表示を防ぐ扱い

- 新しい成功報告では最新データを置き換えます。
- 新しい失敗報告では直近の成功データを保存したまま、APIはunverifiedと空配列を返します。
- 最終成功から6時間以上経った場合もunverified。no_dataと区別します。
- 古い時刻の報告や同じ報告の再送は最新結果を上書きしません。
- 帷子のavailable_candidateは候補のまま。available_in_sourceへの変更は拒否します。
- /availabilityは従来どおり午前/午後/夜間のラベルを保持します。/searchでは施設ごとの時間帯と照合します。
- source_checkedは「取得・解析処理が完了した」という意味です。予約可能性・全件の精度を保証しません。

## Cloudflareで後から必要になる操作

1. 無料プランで空き情報専用D1を作成し、worker.mjsのSCHEMAを実行。
2. 空き情報専用Workerを作成し、D1をDBという名前でバインド。
3. WorkerのシークレットINGEST_TOKENに十分長い専用トークンを登録。
4. 同じトークンをGitHubのリポジトリシークレットに登録（コード・ログ・URLには入れない）。
5. APP_ORIGINに https://keiko-note-9718d.web.app を設定。
6. 手動で送受信・失敗・古いデータ・実際のCPU時間を確認してから毎時検証へ接続。

認証情報の作成と登録はこのPRに含めません。
Freeの利用枠を超えて停止した場合、アプリ側で「取得できません」と表示する設計です。有料プランへの自動切替は行いません。
この設計では施設ごとに1行、合計5行の最新データだけを保持します（履歴の蓄積はしません）。

## 送信の実環境確認

availability-upload-check.ymlは試作ブランチの送信コード変更時、または手動実行時に5施設の取得と保存を行います。毎時処理とは同時実行しません。送信先は専用WorkerのHTTPS URLに固定し、転送を拒否します。INGEST_TOKENはActionsの実行ステップにだけ渡します。認証失敗は再試行しません。一時的な通信失敗のみ1回再試行します。

元の取得処理が出す概要は取得部分のみの説明です。その下の「空き情報サービスへの保存結果」で送信結果を確認してください。

## 毎時の試験運用

five-check.ymlが毎時23分の実行を要求します（開始はGitHub側で遅れる場合があります）。従来の試験期限2026年10月20日00:00 JSTで、予定実行による施設アクセス・送信を停止します。期限後も手動実行は可能です。自動の有料切替・課金契約は行いません。

送信成功後に公開APIから読み戻し、施設・取得日時・状態・全セルが送信内容と一致した場合のみ「保存・読み戻し一致」と表示します。秘密のトークンは読み戻し要求には付けません。現時点では予約可能性や全セルの判読精度は保証できず、帷子は画像更新時に再検証が必要です。

## 日時検索（search_version=1）

2026年10月17日に各施設の公式案内を確認しました。時刻は日本時間（Asia/Tokyo）です。

|施設|午前|午後|夜間|通常の休館・短縮|
|---|---|---|---|---|
|平沼|09:00–13:00|13:00–17:00|17:00–21:00|第4月曜・12/28–1/4。日祝は夜間なし|
|戸部|09:00–13:00|13:00–17:00|17:00–21:00|第3月曜（祝日は翌平日）・12/29–1/3。日祝は夜間なし|
|軽井沢|09:00–13:00|13:00–17:00|17:00–21:00|月曜・木曜・12/29–1/3|
|帷子|09:00–12:00|13:00–17:00|17:00–21:00|火曜・金曜・12/29–1/3。12:00–13:00は閉館|
|菊名|09:00–13:00|13:00–17:00|17:00–21:00|第3月曜（祝日が続く場合も後ろへ移動）・12/29–1/3。日祝は夜間なし|

臨時休館・優先利用等は取得済み予約表の状態で除外します。通常ルールと予約表が矛盾した場合、候補を増やす方向には解釈しません。
祝日は内閣府公表の2026・2027年分（振替休日・国民の休日を含む）を使用しています。それ以外の年はcalendar_unverifiedとして候補を返しません。時間帯・休館日ルールは自動取得ではなく、公式案内が変わった場合はコードの更新が必要です。

### 判定

- 1回の検索は同日内の開始・終了時刻を指定します。日をまたぐ時間、開始以上にならない終了、秒付き時刻、不正な日付は400。終日は営業時間を勝手に補わず、具体的な時間の入力が必要です。
- 区間は開始を含み、終了を含みません。13:00終了なら午後枠は不要、13:00開始なら午前枠は不要です。
- 途中の時間・必要枠が欠ける場合は候補にしません。同じ部屋の全必要枠を確認し、途中で別室に移る案は作りません。
- no_data、取得失敗、最終成功から6時間以上経過、未掲載日・不明状態は空室扱いしません。
- matchesは「公開表の同じ部屋で時間条件が合うもの」です。予約の確約ではありません。
- candidatesは追加の確認が必要なものです。帷子の画像空欄、軽井沢のホール/和室という集約表示、戸部・軽井沢等で複数時間帯にまたがる利用などを分けています。
- 軽井沢は個別のホールA/B・和室1/2を識別できないため、同じ個室を継続利用できるとは判定しません。
- 平沼の連続利用は会議室C・和室の2コマのみ公式案内に明記されています。それ以外の連続利用は要確認候補です。
- 団体登録、月/週の利用回数、抽選・受付状況、定員、音量、稽古内容への適合性は自動確定しません。booking_verifiedは常にfalseです。
- 片付け・清掃時間は利用時間に含まれます。菊名は終了10分前から清掃、終了5分前までに終了する案内があるためnotesで示します。
- /availabilityの形式と送信データのschema_version=1は変更しません。毎時取得側・D1のテーブル・シークレットの再設定は不要です。
- 検索は保存済みの5行を最大1回ずつ読むだけです。検索のたびに施設サイトへアクセスしたり、D1へ書き込んだりはしません。

### 検証とデプロイ

既存の `node --test availability-service/worker.test.mjs` で、HTTP/SQLite保存テストと日時検索テストを一緒に実行します。
検証項目は、13時・17時の境界、帷子の昼休み、日祝の夜間、休館日の祝日振替、年末年始、同室の連続枠、欠測、古いデータ、候補の区別、従来の読み戻し形式です。

1. Cloudflareで **rehearsal-availability-api** の「コードを編集する」を開きます（通知用Workerは変更しません）。
2. このフォルダーの **worker.mjs** 全文で既存コードを置き換えてデプロイします。外部パッケージや追加ファイルは不要です。
3. /health の応答に `"search_version":1` があることを確認します。
4. /facilities に5施設が出ることを確認します。
5. /search?date=2026-10-24&start=13:00&end=17:00 を開き、resultsに5施設が出ることを確認します。空室件数は最新の予約表によって変わります。
6. GitHubのFive facilities availability checkを手動実行し、従来の保存・読み戻しが引き続き一致することを確認します。

この時点では稽古ノートの画面にはまだ追加されません。Cloudflareの新サービス・有料プラン・通知設定の変更は不要です。
